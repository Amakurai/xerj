01·THE AUTOPSY · A STAGE THAT SHIPPED UNMEASURED

FIRST, WE BROKE IT
IN PUBLIC.

The rerank stage — hand BM25's top hits to a hosted relevance judge, reorder by the probability that comes back — shipped with a caveat that said, honestly, quality not verified, no provider key. Then TypeSafe granted this project an evaluation key. The first measured run turned the caveat into a number, and the number was a disaster: 0.3822 nDCG@10 where plain BM25 scored 0.7750. Adding the judge made ranking worse than not using it.

The defect was ours, not the model's. Isolated at the raw API, not guessed: the request builder put every candidate into shared state and asked each question key an untargeted "Does this document contain information that answers the query?" — so "this document" resolved to nothing, and the model judged the whole pile once, echoing roughly that probability back per question. Within every 30-document window the probabilities were near-uniform (spread ≈ 0.02) — query-level noise wearing a ranking's clothes.

FINDING 1

The provider is not deterministic

900 same-document pairs per dataset

The same request, three times: mean per-document probability drift |Δ| 0.0077 (SciFact) / 0.0096 (NFCorpus), max 0.08. Repeat-level nDCG means spanned 0.7422–0.7474 and 0.3285–0.3316. Any comparison of Jev numbers tighter than ~±0.01 nDCG@10 is measuring noise. Our repeats were medians for exactly this reason; a single-shot benchmark of a hosted judge is a coin with a ±0.01 bias.

FINDING 2

The probabilities are not calibrated to BEIR relevance

9,000 + 7,186 (probability, relevance) pairs

Expected calibration error 0.1023 on SciFact, 0.1332 on NFCorpus. The reliability curve is monotone — the model discriminates, it orders documents well — but every bin above 0.2 overstates relevance. On SciFact, documents the model rated around 0.85 were relevant 42% of the time; on NFCorpus, bin 9 is 0.92 confidence / 0.55 actual. A Jev probability is a usable ordering signal and an unusable threshold against graded human labels: setting min_score on the raw number cuts documents the qrels call relevant. The curves are in the result JSONs, bin by bin.

  • About the calibration number you'll meet again below. The local history vote on this site measured ECE 0.012 on Banking77. That is not a scoreboard win over the judge's 0.10–0.13: the vote was in-domain classification against its own training labels; the judge was scored cross-domain against BEIR's graded human relevance. Calibration is a property of the target, not of the interface. Both numbers are honest on their own task, and neither redeems the other.

03·THE WIRE · A XERJ NODE THAT ANSWERS /v1/systemone

THEN WE ASKED THE
QUESTION BACKWARDS.

System One is a documented interface for typed judgement: POST /v1/systemone with a state, a model, and a map of questions, each answered noul (a yes/no with a 0–1 probability) or choice (N named options with probabilities). XERJ already had the retrieval answer for exactly that shape of question: index the labelled history you already have, answer a new question by a rank-weighted vote over its k nearest neighbours, and report the winning label's vote share as the probability — sub-millisecond, BM25-only, no model. So the node learned to speak the wire.

SURFACE 1

POST /v1/systemone

native REST · --port + 1

The documented request and response shape, answered by the vote. A client written for TypeSafe's API works unmodified: state string or object, instructions string / object / array, backtick paths (`documents.doc_0`) resolved against state before the vote text is built, answers keyed exactly by the ids sent — everything the strict clients validate.

SURFACE 2

POST /_decide

ES-compat port · the audit surface

The same vote without the wire costume: it names its index per request, and it returns the evidence — each neighbour's id, label, the engine's own BM25 score, its 1/rank weight, and its text — so any answer can be checked against the history that produced it. Abstains below decisions.min_confidence.

BREAK 1

model is echoed truthfully

deliberate · test-pinned

The response says xerj-history-vote-1, never a Jev model name. Echoing jev-1.13.0 would claim these probabilities are the hosted model's; the requested name rides at decisions.requested_model. This page is about compatibility, and compatibility does not require lying about whose numbers they are.

BREAK 2

Zero support is a 422, never a fabricated 0.5

deliberate · test-pinned

A question whose vote finds no labelled neighbour carries no information. The endpoint refuses it — HTTP 422, naming the question ids — rather than inventing a middle probability. A silent 0.5 is exactly the silent-fake defect class this project treats as a bug, wire compatibility or not.

The gate: the pip client, unmodified, on a local node

No SDK of ours, no patches, no subclassing — pip install jev-reranker (0.1.0, MIT) in a clean venv, its own listwise instruction template, its own splitting, its own strict response validation, pointed at a XERJ node holding 4,000 labelled SMS messages. Two environment variables, and one of them is a trap:

$ # TYPESAFE_ENDPOINT carries the FULL path — TYPESAFE_BASE_URL is silently ignored

The client's own validation is the wire gate — answers keyed exactly by the sent ids, every noul numeric in 0..1, model a non-empty string, usage non-negative integers. Surviving it unmodified is the compatibility claim; the spam/ham separation is the semantic one. Zero requests left the machine: the vote is an ordinary search of an ordinary index, and the module adds no outbound client.

The first gate attempt failed, and the failure is the most useful thing on this page. The wire puts the query in state, and the vote text joins it — so query vocabulary participates in retrieval. With a spam-bearing query ("winner claim prize"), every document retrieved spam neighbours and the vote measured the query, not the documents: spam 1.000 vs ham 0.785, no separation. The fixed gate uses a query whose every term is absent from the corpus ("triage inbox unsolicited correspondence"): 0.9014 vs 0.0956. This is inherent to a retrieval vote, not a defect to fix — pick the query for the history you have, and don't let a rerank-shaped habit leak vocabulary into a classification-shaped question.

  • Read this before quoting the compatibility claim. The node did not "become a language model." It answers a typed judgement wire from a search over your own labelled history, says so in its model field, refuses what it cannot know (zero support, score-type ordinal questions), and attaches the neighbours that produced every answer. If you need judgement where you have no history — a new policy, an unseen category — this is the wrong tool, and the hosted judge is the right one. The two ends of the wire are complements, not competitors.

  • Both columns survive contact with the other's weakness. The judge is the only option where there is no history — and every call is metered, slower, and ships document text to a third party. The vote is free, sub-millisecond, and never leaves the node — and it cannot judge anything your history doesn't already cover. At 300 queries a day the judge costs $0.40 and is irrelevant to your budget — use it freely. At 300,000 messages a day it is 1.49 s each — 124 hours of provider latency per day, however you parallelise it — plus a bill of roughly $400 a day at this run's measured rate, plus every one of those messages leaving the node. The vote answers each in under a millisecond, on the node, for nothing.
  • Why the wire matters more than either number. Every System One client — the reranker, the SDKs, whatever an agent is already holding — now has a second, local implementation of the interface it speaks. Point TYPESAFE_ENDPOINT at a XERJ node when the questions have history and must stay home; point it at the hosted API when they don't. Same client, same wire, no code change — that is the whole bridge.
What we claim, and what we do not. Claimed: every number on this page, from the runs cited beside it, on our node, our shortlists, the pinned model. Not claimed: anything about how Jev scores on Banking77 or SMS (TypeSafe has published no such numbers and we ran none — which is why those tables carry no judge row); any zero-shot ability for the local vote; that the published hosted-reranker figures and ours are comparable beyond dataset and metric. TypeSafe AI granted the evaluation key that made §01–§02 possible — the measurements are of their model, through their documented API, and this project thanks them for the access. The findings here are ours, warts published.

$ cargo build --release -p xerj-server
$ cat > gate.toml <<'EOF'
[decisions]
index          = "sms"
k              = 10
label_field    = "label"
text_field     = "text"
positive_label = "spam"
min_confidence = 0.0
EOF
$ ./target/release/xerj --insecure --port 9440 --config gate.toml # native REST on 9441
